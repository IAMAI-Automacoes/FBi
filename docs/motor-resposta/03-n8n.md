# Motor de Resposta — Especificação do lado n8n

Documento para **você** montar os fluxos no n8n. Não é node-por-node: é o contrato.

> **Atualizado em 2026-08-26, a pedido do Raver (dono do produto):** o desenho original (§7 abaixo) empurrava a
> mensagem pro n8n via webhook, assim que ela ficava pronta. Trocado por **puxar**: o Supabase só deixa a
> mensagem pronta numa fila; o n8n lê essa fila **uma vez por dia** e manda o que encontrar. A razão de ser do
> antigo §7 (não dar ao n8n lógica de negócio) continua valendo — só a direção da leitura mudou, a fila e o
> cooldown continuam 100% calculados no Supabase.

Decisões que fixam este desenho:
- **n8n só entrega e confirma.** Toda a lógica de negócio (fila, cooldown, lock, agrupamento, LLM) vive no
  Supabase. O n8n não decide QUANDO mandar — ele só lê o que já está marcado como pronto.
- **n8n lê via REST com a service key, não via Postgres direto.** Uma `view` plana (`fila_envio_n8n`) evita
  qualquer join do lado do n8n. Ele escreve de volta chamando a Edge Function de callback (já existia, não
  mudou) — mesmo padrão do `x-cron-secret` que os crons já usam.

Consequência prática: o fluxo novo tem um gatilho diário, um `GET` na view, um loop mandando pro WhatsApp, e um
callback por mensagem. Se você precisar mudar cooldown, agrupamento ou texto, muda no Supabase, não no n8n.

## 1. Panorama — quem faz o quê

```
  ┌─ SUPABASE ─────────────────────────────────────────────┐
  │                                                         │
  │  pg_cron (a cada 5 min)                                 │
  │      │ pg_net                                           │
  │      ▼                                                  │
  │  Edge Function: motor-retorno-worker                    │
  │      · lê a fila de avisos pendentes                    │
  │        (só os com mais de 2h de vida — ver §2.5)         │
  │      · calcula max(criado_em+T_AGG, ultimo+T_COOLDOWN)  │
  │      · lock por contato (linha com dono e prazo)        │
  │      · agrupa por ação → por feedback → desempate       │
  │      · chama OpenRouter (monta o texto)                 │
  │      · grava mensagem_enviada (status='pronta')          │
  │      · PARA POR AQUI — não fala com o n8n                │
  │                                                         │
  └─────────────────────────────────────────────────────────┘
         ▲
         │ GET  (uma vez por dia, via n8n)
         │
  ┌─ N8N ───────────────────────────────────────────────────┐
  │  Schedule Trigger (1x/dia)                               │
  │      · GET fila_envio_n8n (view, status='pronta')        │
  │      · para cada linha: POST uazapi  /send/text           │
  │      · sucesso ou erro → callback, por linha              │
  └──────┼──────────────────────────────────────────────────┘
         │ POST  https://<proj>.supabase.co/functions/v1/motor-retorno-callback
         ▼
  ┌─ SUPABASE ─────────────────────────────────────────────┐
  │  Edge Function: motor-retorno-callback (não mudou)       │
  │      · valida x-motor-secret                             │
  │      · UPDATE mensagem_enviada → 'enviado' | 'falhou'    │
  │      · avisos → 'enviado'  |  volta para 'na_fila'       │
  │      · atualiza janela_contato.ultimo_envio_em           │
  └─────────────────────────────────────────────────────────┘
```

**Ponto que não pode ser violado:** o `ultimo_envio_em` (o relógio do cooldown de 3 dias) só avança **quando o
callback confirma entrega**. Se o n8n cair ou demorar a rodar, a mensagem continua 'pronta' e sai na próxima
leitura diária — nada se perde (invariante I3). Enquanto uma mensagem estiver 'pronta' esperando o n8n, o worker
não compõe outra pro mesmo contato — evita duas mensagens no mesmo dia se a leitura diária atrasar.

### 1.5 A espera de 2 horas (debounce de status)

Uma transição de status só vira candidata a virar mensagem depois de **2 horas sem ser revertida**. O dono muda
o card errado e corrige em 10 minutos → nada é gerado, nunca existiu aviso pra cancelar. Depois das 2h, se a
ação voltar pra um status anterior, o aviso pendente daquela transição é cancelado do mesmo jeito (isso já
existia antes das 2h entrarem — não é coisa nova, só continua valendo). Isso é 100% Supabase; o n8n não sabe
que essa espera existe.

## 2. Fluxo A — `easyfeed-enviar-retorno` (o novo, o que você vai criar)

### Gatilho
Nó **Schedule Trigger**, uma vez por dia (horário sua escolha — sugestão: cedo da manhã, fora do `quiet_hours`
padrão de 22h–9h). Nada de webhook aqui: quem inicia o fluxo é o relógio do n8n, não o Supabase.

### Ler a fila
Nó **HTTP Request** (`GET`) contra a view, que já vem pronta (sem join nenhum do seu lado):

```
GET https://lixrcruilisncfhfhndo.supabase.co/rest/v1/fila_envio_n8n?select=*
headers:
  apikey:        <SUPABASE_SERVICE_ROLE_KEY>
  Authorization: Bearer <SUPABASE_SERVICE_ROLE_KEY>
```

Cada linha devolvida é uma mensagem pronta pra sair — o Supabase já decidiu que o cooldown de 3 dias passou
(não confia no relógio do n8n pra isso, o corte já veio filtrado). Formato de cada linha:

```jsonc
{
  "mensagem_id": "b3f1…-uuid",          // idempotência: mesmo id = mesma mensagem
  "restaurante_id": 11,
  "restaurante_nome": "Cantina do Zé",
  "whatsapp_token": "…",                 // de restaurantes.whatsapp_token (instância do restaurante)
  "whatsapp_base_url": "https://…",      // de restaurantes.whatsapp_base_url
  "contato_id": "9a2c…-uuid",
  "telefone": "5511932903005",           // 13 dígitos, sem '+', pronto para a uazapi
  "texto": "Oi! Você comentou sobre a demora…",  // JÁ montado pela IA, envie literal
  "feedbacks_originais_ids": ["…uuid…"],       // rastro — não precisa usar, só existe pra auditoria
  "feedbacks_restaurante_ids": [123, 456],     // idem
  "criado_em": "2026-08-25T14:00:00Z"
}
```

Notas:
- **`texto` vai literal.** Não reescreva, não concatene saudação, não adicione assinatura. Já respeita
  `max_itens_msg` e já foi montado com os blocos agrupados. Qualquer edição no n8n quebra as invariantes.
- **`mensagem_id` é a chave de idempotência.** Se o mesmo `mensagem_id` aparecer de novo (o dia seguinte, se
  algo falhar no meio), o callback do Supabase é idempotente e uma segunda confirmação não faz nada.

### Loop — para cada linha da fila
1. **Split In Batches / Loop Over Items** sobre o resultado do `GET`.
2. Chama a uazapi. **Formato confirmado** pelo nó `HTTP Request` do workflow `Feedback Restaurante Uazapi`
   (export de 2026-08-24) — é exatamente o mesmo do ack:
   ```
   POST {{ $json.whatsapp_base_url }}/send/text
   headers: { "token": "{{ $json.whatsapp_token }}" }
   body:    { "number": "{{ $json.telefone }}", "text": "{{ $json.texto }}" }
   timeout: 5000
   ```
   `telefone` já vem com 13 dígitos, sem `+` e sem `@s.whatsapp.net`. **Não aplique `.split()` nem nenhum
   tratamento**; o Supabase já normalizou.
3. Ramo de sucesso → callback com `status: "enviado"`.
4. Ramo de erro (nó de erro / IF sobre o status HTTP) → callback com `status: "falhou"` + o motivo.

⚠️ **Não repita o bug do fluxo atual.** No workflow de entrada, o nó `HTTP Request` (ack) tem o token
**hardcoded** (`469bb609-…`) em vez de usar a variável, o que quebra multi-tenant. Aqui o token **tem** que sair
de `{{ $json.whatsapp_token }}` — ele muda por restaurante.

⚠️ **O ack atual não checa o resultado do envio** — não há nó de erro depois do `HTTP Request`, então falha
some. No fluxo novo o ramo de erro é obrigatório: é ele que devolve os avisos para a fila.

Sem `Wait`, sem lógica de agrupamento, sem cálculo de cooldown. Se você sentir vontade de adicionar um desses, é
sinal de que algo foi parar no lugar errado — me avise.

### O que o fluxo devolve para o Supabase (callback, uma chamada por linha)

`POST https://lixrcruilisncfhfhndo.supabase.co/functions/v1/motor-retorno-callback`, header
`x-motor-secret: <segredo>`:

```jsonc
// sucesso
{ "envio_id": "b3f1…", "status": "enviado",
  "provider_message_id": "…",     // se a uazapi devolver algum id
  "enviado_em": "2026-08-24T20:31:05Z" }

// falha
{ "envio_id": "b3f1…", "status": "falhou",
  "erro_codigo": "HTTP_401",       // ou timeout, numero_invalido, instancia_desconectada…
  "erro_mensagem": "texto cru da resposta da uazapi" }
```

`envio_id` aqui é o mesmo `mensagem_id` que veio na leitura da fila. Em caso de falha o Supabase devolve os
avisos para `na_fila` e **não** avança o cooldown — a mensagem volta a aparecer em `fila_envio_n8n` (depois que
o worker reprocessar) e sai na leitura diária seguinte, em vez de se perder.

## 3. Fluxo B — o ack (`Feedback Restaurante Uazapi`, já existe)

**Não mexer.** ✅ Verificado no export: o ack **não toca** nada de fila ou cooldown. I7 está garantida por
construção, não por convenção.

O que ele faz hoje, resumido:

```
Webhook /webhook/easyfeed → filtros (evento, grupo, fromMe)
  → Verifica Restaurante (numero_whatsapp = chat.owner)
  → Onboarding completo? → É pagante?
  → audio (transcreve) | texto
  → message_buffer: Gravar → Ler → Ordenar → Switch(20s) → Limpar   ← debounce de rajada
  → Formatar Texto → AI Agent1 (sentimento) → If (descarta Sem_Avaliacao)
  → INSERT feedbacks_originais
  → Basic LLM Chain (fatia em pontos)
  → Trata as mensagens ─┬→ If1 → INSERT feedbacks_restaurante (origem_id)
                        └→ If2 → POST /send/text     ← O ACK
```

**O texto do ack é fixo**, sorteado entre 12 frases prontas em 4 cenários (positivo/negativo/misto/neutro), no
Code node `Trata as mensagens`. Não é LLM. Continua assim.

**Regra permanente:** o ack **nunca** pode escrever em `janela_contato.ultimo_envio_em` nem inserir em
`aviso_pendente`. Se um dia alguém for tentado a "aproveitar" o ack para registrar contato, isso quebra I1 e I7.
O ack segue sendo o único retorno para quem mandou feedback que nunca virou ação (SPEC, Parte G).

### Integração com o ack: NENHUMA ✅ (decisão de 2026-08-24)

O motor precisa de `contato_id`. **Decidido: resolver no Supabase, por trigger.**

Um `BEFORE INSERT` em `feedbacks_originais` faz o upsert em `contatos` por `(restaurante_id, telefone)` e
preenche `contato_id`. O telefone chega do n8n já normalizado (`chatid.split('@')[0]`, 13 dígitos), e a trigger
aplica a normalização de novo por garantia — se um dia o gateway mudar de formato, o motor não quebra.

**Consequência: o workflow `Feedback Restaurante Uazapi` fica 100% intocado pela feature.** Nenhum nó novo,
nenhuma edição. Ele continua fazendo exatamente o que faz hoje.

### Bugs no fluxo de entrada — adiados (decisão de 2026-08-24)

Ficam documentados, não entram nesta tarefa. **Nenhum deles bloqueia o motor.**

1. **Token hardcoded** em `baixa_audio` e `HTTP Request` (`469bb609-…`).
   > Levantou-se que esse token seria universal da conta uazapi. **Verifiquei no banco: não é.** Restaurante 11
   > (Camelo) tem `469bb609…`; restaurante 13 tem `138e7e7e…` — ambos ativos, tokens distintos. O universal é
   > `whatsapp_admin_token` (`YO3H6W6P…`), que usa header `admintoken:`, outro escopo. Detalhe e tabela completa
   > na auditoria, §1.3.
   >
   > **Efeito hoje:** o ack do restaurante 13 sai pela instância do 11 — número errado para o cliente.
   > **Efeito no motor: nenhum** — o fluxo novo lê `restaurantes.whatsapp_token` por restaurante.
2. `Informações Feedback1` grava `sentimento` duas vezes (`$json.Sentimento` inexistente + `$json.output`).
3. O `text` do ack concatena `resposta_cliente` + `feedback_original`; o segundo resolve vazio.
4. Restaurante não-pagante → `AI Agent` + `HTTP Request2`, ambos `disabled` → silêncio sem log.
5. `remote_id` = `"remote_id" + telefone`, sem `restaurante_id` → buffers colidem se a mesma pessoa mandar
   feedback a dois restaurantes na mesma janela de 20s.

## 4. Fluxo C — o disparo atual por mudança de status (o que sai)

Hoje **dois** caminhos disparam o n8n na mudança de status:

| # | Onde | O quê |
|---|---|---|
| 1 | `src/components/actions/TaskBoard.tsx:363-376` → edge fn `webhook-n8n` → secret `mensagem_follow_up_feedback` | frontend, fire-and-forget |
| 2 | Trigger **`Status_feedback`** em `acoes_operacionais` → `…/webhook-test/status_açoes` | banco, `AFTER UPDATE` em **qualquer** coluna |

O nº 2 não está em nenhuma migration — foi criado direto no banco. Ele dispara até quando você só reordena o
board (`atualizarOrdemAcoes` faz N UPDATEs em paralelo).

**Plano de corte, na ordem:**

1. Criar o fluxo A e testá-lo com um payload manual.
2. Ligar o motor no Supabase **com a mensagem ainda não sendo enviada** (modo dry-run: grava
   `mensagem_enviada` mas não posta no n8n). Confere-se a fila e os agrupamentos sem incomodar ninguém.
3. **Só então** desligar os dois caminhos antigos, na mesma janela:
   - remover o bloco em `TaskBoard.tsx:363-376`;
   - `DROP TRIGGER "Status_feedback" ON public.acoes_operacionais;` (em migration, para ficar versionado).
4. Tirar o dry-run.

Fazer o passo 3 antes do 2 abre janela de silêncio; fazer o 4 antes do 3 gera mensagem duplicada. Essa ordem
evita as duas coisas.

**No n8n:** depois do passo 3, o que quer que escute `status_açoes` fica sem tráfego. Desative (não delete ainda
— deixe uma ou duas semanas como rede de segurança).

O secret `mensagem_follow_up_feedback` e a edge function `webhook-n8n` também saem, **desde que nada mais os
use**. Como `webhook-n8n` é um proxy cego que repassa qualquer payload, ele pode estar servindo outra coisa além
do disparo de status — vale um olhar antes de remover.

> **Decisão de 2026-08-24:** não vou pedir o export do workflow consumidor. O fluxo do motor é novo e separado;
> o antigo só precisa ser desligado, não entendido. **Mas o desligamento é obrigatório, não opcional** — o
> trigger `Status_feedback` está `active` em produção agora, disparando a cada UPDATE de `acoes_operacionais`.
> Se ele sobreviver ao go-live do motor, o cliente recebe duas mensagens por transição: a do motor e a do
> caminho velho. É literalmente o bug que a feature existe para matar, voltando por outra porta.
>
> Risco residual assumido: se algum outro workflow depender daqueles POSTs para algo que não seja mensagem ao
> cliente, isso quebra silenciosamente no corte. Não tenho como descartar sem o export. Se você souber que não
> há nada, seguimos.

## 5. Tabelas que o n8n lê ou escreve

**No fluxo novo (`easyfeed-enviar-retorno`): lê a `view` `fila_envio_n8n` (GET via REST, sem join do seu lado)
e escreve só via o callback — nunca direto numa tabela.**

Nota de contexto: o **fluxo de entrada** já escreve direto no banco com a credencial `Feedback Restaurante`
(`J3N40FgVQE4DIL2U`) — `restaurantes` (SELECT), `message_buffer` (INSERT/SELECT/DELETE), `feedbacks_originais` e
`feedbacks_restaurante` (INSERT). Isso continua como está; não vou mexer.

O que a `view fila_envio_n8n` expõe (uma linha = uma mensagem pronta):

| Campo | Tabela de origem |
|---|---|
| `telefone` | `contatos.telefone` |
| `texto` | montado pelo worker a partir de `aviso_pendente` + `acoes_operacionais` + `feedbacks_originais` |
| `whatsapp_token`, `whatsapp_base_url` | `restaurantes.whatsapp_token`, `restaurantes.whatsapp_base_url` |
| `restaurante_nome` | `restaurantes.nome_restaurante` (só para contexto/log) |
| `feedbacks_originais_ids`, `feedbacks_restaurante_ids` | rastro de quais feedbacks motivaram esta mensagem — não precisa usar pra enviar, existe pra auditoria |
| resultado do envio | escrito em `mensagem_enviada` **pelo callback**, não pelo n8n |

Tabelas do motor, pra você situar: `contatos`, `aviso_pendente`, `janela_contato`, `mensagem_enviada`,
`feedback_acao` (o vínculo N:N ação↔feedback original).

## 7. Por que o desenho original evitava o n8n orquestrar (revisado em 2026-08-26)

Registro da decisão original, mantido por contexto — e do que mudou.

O motivo de ORIGEM continua de pé e não foi revertido: o agrupamento (Passada 1 → Passada 2 → desempate), o
lock por contato, o cálculo de cooldown e a espera de 2h (§1.5) continuam **inteiramente** no Supabase,
testados (`npm test`) e versionados neste repo. Nada disso foi movido pro n8n.

O que mudou foi só **quem inicia a conversa**: antes o Supabase empurrava (`fetch` pro webhook do n8n) assim
que uma mensagem ficava pronta; agora o Supabase só deixa pronta, e o n8n **puxa** uma vez por dia, por decisão
explícita do dono do produto — que preferiu essa cadência a depender de um webhook sempre no ar do lado do n8n.
Trade-off aceito conscientemente: uma mensagem pode ficar "pronta" esperando até ~24h antes de sair, mesmo que o
cooldown de 3 dias já tenha liberado antes disso. Se um dia isso incomodar, aumentar a frequência do Schedule
Trigger resolve sem mexer em nada do lado do Supabase.
